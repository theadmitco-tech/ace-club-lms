# Student batch access — 25 October 2026

The user confirmed: “They only see their enrolled batch.”

This resolves the Student schedule eligibility question in the decision register.
A product purchase does not expose every published batch of that product. A
Student must have an active enrollment in the batch, an active Student profile
and current entitlement to that batch's exact product. Only the latest published
snapshot is visible. Unpublishing, enrollment removal, account deactivation,
expiry or purchase revocation removes access on the next read.

V2 batches have separate identities from legacy courses. Explicit V2 batch
membership records therefore connect Students to these schedules. Admins can
record or remove membership for existing Students; this does not create accounts,
purchases, grants or legacy enrollments. Membership alone cannot grant access.
An existing enrollment is retained for history when product access expires.

This decision does not define Full Course allocation among constituent live
courses, paid seat allocation, registration checkout, automatic enrollment from
payments, or the public registration catalogue. The enrollment screen records
schedule membership; it is not the eight-seat registration allocator. Keep the
feature disabled for shared delivery until those operational boundaries and the
candidate's staging setup are reviewed. There is no automatic enrollment of
existing Students and no uniqueness rule limiting a Student to one batch across
all purchased products.

Private Meet links, protected recordings, content mappings and shared migration
approval remain separate. The new migration is proposed and tested locally only.
The original 20 October decision source remains unchanged.
