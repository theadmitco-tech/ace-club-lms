# Owner-operated Google signup and resource acceptance

Status: procedure prepared; hosted execution and acceptance remain pending. This plan covers the genuine Google signup and deliverable resources that the twenty-account synthetic fixture inventory deliberately excludes. It is not an executable cleanup packet or evidence of a completed test.

The deployment owner or designated staging operator performs hosted actions. Engineering prepares and rehearses exact packets locally using synthetic records, then reviews sanitized results. Production, Live Mode payments, existing libraries and the existing walkthrough remain excluded from mutation. Credentials, account identifiers, resource references and provider records remain private.

## Required inputs before execution

- The exact deployed candidate SHA and Preview origin, staging project `eyphkkginlgoaxflauog`, working Google callback and reachable signed Razorpay Test Mode webhook require owner confirmation.
- A designated disposable Google identity requires owner-controlled sign-in/MFA and confirmation that it has never existed in the staging Auth directory. Its email must not be inferred from a synthetic account. No such identity is recorded by this plan.
- A separate private run manifest, fresh application/ledger baseline, exact Auth/profile observations and storage-object inventory must precede signup. The operator first completes cleanup of the synthetic twenty-account run; the two cleanup baselines must not overlap.
- A harmless, owner-approved PDF and short MP4/WebM, and an authorized external reading or recording if provider rendering is included, require exact file hashes and intended resource locations. Existing real library references must not be copied or modified by default.
- A private cleanup packet must be generated for the exact new identity, payment records, isolated courses and uploaded objects, reviewed and rehearsed against a disposable local reconstruction before hosted mutation. The existing synthetic cleanup generator rejects a genuine Google identity and cannot be reused by substituting its email or bypassing validation. That separate packet and its fresh baseline are not yet prepared.

If any prerequisite is missing, its associated gate remains pending. No generated provider metadata, existing active account or example.invalid resource substitutes for genuine signup, playback or delivery evidence.

## Account boundary

| Identity | Permitted acceptance use | Preservation and cleanup |
| --- | --- | --- |
| Existing designated Student or Admin | Sign-in, navigation and read-only inspection within current access | Identity, role, active state, purchases and original records remain intact. No payment, feedback, playback observation or publication writes are performed under this plan. Any additional stateful walkthrough needs a separate scoped plan. |
| New disposable Google identity | Fresh Google callback, initially inactive/unpaid access denial, captured Test Mode payment and automatic access/activation, then learning/resource checks | Before-signup absence and after-signup exact Auth UUID, provider identity, creation time, email and profile must match private observations. The identity remains separate from the twenty generated accounts. Only that new identity and its explicitly tracked test activity qualify for cleanup. |
| Existing designated Admin performing setup | Approved creation/publication of new isolated test content only | The account is never deleted or re-roled. All resulting test-owned rows are tracked by exact IDs and references, including audit rows with the existing Admin as actor. Actor identity alone is never a deletion selector. |

A signup that resolves to an existing Auth identity stops the fresh-signup case. The operator neither deletes that identity nor deactivates it to simulate first signup. Unexpected activity or ambiguous ownership stops cleanup for reconciliation.

## Isolated execution and evidence

1. The operator records a unique run ID, exact candidate SHA/origin, UTC start time, original table counts/fingerprints and ledger fingerprint privately. Staging activity is paused for the bounded baseline interval; any unrelated change is investigated rather than overwritten.
2. New test-only templates, batches and publication revisions are created with explicit run ownership. Every template, batch, session/resource key, content item/revision, publication request/audit and enrollment ID is recorded. Original courses, templates, placements and the walkthrough are unchanged.
3. Sample uploads use new run-specific object paths. The manifest records bucket, exact path, content hash and resource/placement IDs; it verifies object absence before creation. External provider links require permission and do not establish private-storage protection.
4. The disposable identity signs in through real Google. Before payment, the operator verifies initial signup state and denial of protected content. After a captured Test Mode payment, the application must activate the eligible identity and grant only the paid subjects/enrollments without manual activation. Exact checkout, order, payment, event, purchase, grant, upgrade and live-registration references are recorded privately.
5. The operator opens the isolated protected PDF and recording, checks navigation and applicable feedback, and tests replacement/unpublication denial using only the test content. Progress, watch sessions/samples, obligations, feedback, completion and resource audit rows are tracked. Student access to unrelated subjects remains denied. No genuine attendance is asserted by simulated live events.
6. The report records expected/observed results, exact candidate, time and evidence provenance. Genuine Google/provider delivery, manual usability observations and automated assertions remain distinguishable. Public reports omit account details, private URLs, secrets and raw provider payloads.

## Exact cleanup and stop conditions

Before cleanup, all recorded checkouts require a known terminal or explicitly reconciled state; provider delivery is restored after any interruption test. Delayed or ambiguous payments stop cleanup. Razorpay Test Mode history is retained and requires no real refund. Disabling `V2_CHECKOUT_TEST_ENABLED` also disables webhook handling; it must not be treated as a new-order-only pause.

The reviewed private packet validates staging context, exact run identity and original-row preservation, then removes only enumerated test-owned application rows in foreign-key-safe order within one transaction. It verifies each row against its expected identity/references before deletion and rejects unexpected rows or revisions. Generated enrollment, access, payment, learning and content records must be accounted for explicitly; no selection by email domain, actor ID alone, broad course prefix or creation time alone is sufficient. Original row multiplicities, the original ledger and unrelated data must match the baseline after cleanup. Existing foreign-key restrictions remain enabled.

Storage is cleaned separately through supported Storage operations, using only exact manifest bucket/path pairs after proving run ownership and no retained references. Object absence is checked independently. A failed object deletion leaves cleanup pending; no bucket-wide deletion or direct Storage metadata deletion is permitted.

Only after successful application cleanup and fresh absence checks may the operator delete the exact disposable Auth UUID. Its identity and creation time must still match the original signup record, and remaining purchases, checkouts, references or unexpected activity block deletion. The provider's Google account itself is not deleted. Auth, profile, signup-candidate and related application-row absence are checked independently afterward.

The final receipt includes restored application/ledger fingerprints, zero tracked objects and zero disposable Auth/profile/candidate records. Existing designated accounts and libraries require preservation checks, not deletion. Baseline mismatch, unexpected state or incomplete cleanup remains an open acceptance item; a new baseline cannot be substituted to conceal the discrepancy.
